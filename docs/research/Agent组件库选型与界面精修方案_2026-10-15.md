# Agent 组件库选型与界面精修方案

核查日期：2026-10-15。当前阶段：候选已核查，等待用户选定主组件体系。尚未安装组件库、迁移前端或修改后端。

## 先看结论

**优先看 assistant-ui、shadcn/ui 新 AI Elements、prompt-kit 三种方案。**它们分别适合“完整 Agent 聊天交互”“统一且可自主定制的组件体系”“轻量精致的对话界面”。这是基于文档、源码和现有工程的选型判断，不是已完成接入或视觉对照实验的结果。

不要通过组件数量、GitHub Star 或社交转发量选库。应看同一段长研究答案，在消息、执行状态、引用、记忆、异常和手机输入中是否容易理解。选一个主体系，再补少量兼容组件。

## 本次搜索中需要纠正的旧信息

### 1. 旧 Vercel AI Elements 与 shadcn 新方案要分开

Vercel 官方仓库公告：旧项目将于 **2026 年 11 月底弃用并迁往 shadcn/ui**。这不意味着已经复制的源码届时无法运行，但新一轮改造应优先评估新的维护路径。[官方迁移公告](https://github.com/vercel/ai-elements#readme)

shadcn 的 2026 年 10 月更新新增 Trace，并将聊天、工具、来源等组织成可复制的 AI 界面模式；新项目不必为了使用这些展示模式先换掉现有 Node 任务服务。[新方案与迁移表](https://ui.shadcn.com/docs/ai-elements) · [发布说明](https://ui.shadcn.com/docs/changelog/2026-10-ai-elements)

Trace 的现成状态是 running/error/pending；完成、取消、旧版本失效等业务含义仍需我们明确映射，不能只用动画表示完成。[Trace API](https://ui.shadcn.com/docs/components/base/trace)

### 2. 有 Memory 组件，不代表有长期记忆系统

assistant-ui 的 MemoryChips 支持独立 props 驱动。官方明确说它没有内建的用户记忆概念；示例只是从 remember 工具调用取值、展示及提供删除入口。我们已有的来源、版本、停用、删除及 M09 写入限制仍由原后端负责。[MemoryChips 机制](https://www.assistant-ui.com/elements/memory-chips)

其 ExternalStoreRuntime 可以适配已有应用状态，不强制改用 AI SDK。若选 A，可先接独立展示组件，再决定是否需要完整 runtime。[外部状态适配](https://www.assistant-ui.com/docs/runtimes/custom/external-store)

### 3. Tool UI 不再当作独立维护的主候选

旧 Tool UI 仓库已于 2026-09-26 归档；原 Gallery 当前重定向至 assistant-ui Elements。可借鉴其结构化工具结果设计，但不应与 assistant-ui 重复计数，也不宜先依赖归档入口。[归档仓库](https://github.com/assistant-ui/tool-ui) · [当前目录](https://www.assistant-ui.com/elements)

## 当前界面，具体应该改哪里

依据本地源码审查，不是本轮重新完成全部视觉验收：

| 优先级 | 现状与代码位置 | 本轮选库后应达到的效果 | 可借用部件 |
| --- | --- | --- | --- |
| P0 | `styles.css`、`workspace.css` 与两份功能 CSS 相互覆盖 | 统一字体、颜色、间距、圆角、焦点和状态 token；组件只留必要业务样式 | 所选库的主题与 Button/Tooltip/Tabs/Sheet/Dialog |
| P0 | `App.jsx` 的输入区、辅助按钮、错误提示为手工组合 | 输入、发送、停止、修改、提交失败属于同一组件规范；中文输入期间不误发送，小屏按钮便于点按 | Composer/PromptInput/Sender |
| P0 | `RunStatus.jsx` 以段落和 JSON 入口为主，Bot 交流是长记录 | 默认一行可读的真实进度，按需展开具体工具；失败、取消、旧版本各有清楚表现，回答保持可见 | RunActivity/Trace/ThoughtChain |
| P0 | `ResearchDecision.jsx` 的依据是单独按钮，`App.jsx` 来源区原文很长 | 主张旁看到对应来源；展开可核对公司、期间、单位和定位。只格式化实际取得的字段，不造新的判断 | Sources/InlineCitation/Popover/DataTable |
| P1 | `PersonalMemory.jsx` 管理条目较长，`ResearchContext.jsx` 同时承载范围和关注 | 主回答附近轻量显示本次沿用/已更新；完整来源、修改、停用仍在管理区。个人记忆与本轮任务范围区分 | MemoryChips + Sheet + 现有领域组件 |
| P1 | 会话列表只取本机索引，当前无搜索或日期分组 | 从公司与问题快速找回研究，展示当前选择和演示标记；功能只能以现有持久化能力为依据 | ThreadList/Conversations/Sidebar/Command |
| P1 | 当前 Markdown 直接用 ReactMarkdown，未配置通用表格渲染 | 中文长文、表格、引用、列表和错误块使用一致排版；不能因组件动画冒充真实 token 流 | 所选库的 Markdown/Message/ChatContainer |
| P1 | 滚动与抽屉焦点逻辑手工维护 | 用户向上读时不被新结果拉走，必要时显示回到底部；抽屉关闭回到入口，手机无横向溢出 | MessageScroller/ScrollAnchor/Sheet |

记忆管理不是强迫用户先填写画像；用户也不需要阅读所有 Bot 记录才能理解主回答。界面中的公开执行摘要来自已记录状态，不新增模型隐式思考内容。

## 三个主要方案怎么选

### A：先把通用 Agent 体验做完整

采用 assistant-ui 作为主聊天交互体系，先用独立活动、来源部件；统一通用控件。适合重视工具状态、会话交互和后续扩展。风险是换整套 runtime 时要维护适配层，不能产生两套任务真源。

### B：先把整个界面做成统一、可自主控制的设计系统

采用 shadcn/ui 新 AI Elements 模式，聊天、输入、Trace、来源和侧栏都在同一体系内。适合希望细致控制外观和组件边界。需要自己组织领域卡片，且新发布组件应先用一个完整任务试接。

### C：先把对话界面的质感做好，保持实现轻量

采用 prompt-kit 的消息、输入、工具与来源组件，补齐必要通用控件。适合重视克制排版、长文阅读和细节定制。它提供视觉积木，不负责现有研究任务、记忆和恢复机制。

我的倾向是先比较 **A 与 B**；若你最喜欢轻量对话式样例，再选 C。若偏好 Ant/Lobe 的工作台形式，D/E 也可以作为主体系。最终由用户选择，不自动把调研建议当作安装授权。

## 选定后的最小试接与验收

先接一个真实保存的任务：同一问题、同一结果、同一来源、同一记忆状态。依次验证空态、长答案、工作中、工具失败、取消、修改关注点、记忆停用、资料抽屉和手机输入。缺少可回放状态时明确标注演示，不把静态样例冒充真实调用。

第一批只替换聊天壳、输入、活动和依据组件；保留 MCP、Node API、任务 revision 和个人记忆。试接通过后再统一全界面，移除被替代的 CSS。不能同时装三套聊天 runtime 供产品长期混用。
