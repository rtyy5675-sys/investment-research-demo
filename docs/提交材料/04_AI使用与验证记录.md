# AI使用与验证记录

## 一、谁负责什么

本项目使用 Codex 辅助需求梳理、开源组件调研、编程、调试、测试执行及文档整理。候选人在持续对话中提出和确认产品方向、用户体验要求、首版范围及验收取舍，提供批评与修正反馈；Coding Agent 据此实现并用代码、运行记录和界面核对。

产品运行阶段使用可配置的模型 API 进行研究规划、证据解释和最终回答核验。公网当前实际验证的是 DeepSeek；本机也有 Codex CLI 运行记录。OpenAI 兼容格式有模拟检查，但不能据此声称已完成真实 OpenAI API 验收。

扶摇 MCP 提供真实财务资料；公告与财报 PDF 用于受支持字段的补查。程序处理取证执行、字段/引文校验、算术、版本和预算。最终核验模型也是 AI，其“通过”不是独立专家结论。

## 二、候选人通过讨论作出的关键选择

| 选择 | 理由及落实 |
| --- | --- |
| 先证明一条任务链 | 在时间限制内，优先完成真实取证、解释、补查与判断更新 |
| 从多 Bot 展示转向个人 Agent | 产品主线是少重复交代、持续理解与推进；角色协作留在侧栏 |
| 只交付核心记忆最小链路 | personal agent 是确定方向，主动跟踪和更广泛研究能力属于后续版本 |
| 不固定演示公司 | 公司和报告期从当前问题解析，既有公司只作验收实例 |
| 不把疑问记成立场 | 用户关注、AI 理解、研究状态和确认看法分开；允许不表态 |
| 免费云端只展示实例内连续性 | 明确重启会影响记录，不用本机持久化证明云端长期记忆 |

以上来自本次需求对话和另一段需求/部署整理对话，已与当前实现、测试和公开部署状态对齐，没有将原对话整段当作评审文档或用户访谈证据。

## 三、AI或实现出错后怎样修正

| 真实问题 | 如何发现 | 修正与验证 |
| --- | --- | --- |
| 将“是否得到现金支持”改成用户肯定主张 | 对回答与用户问题的归属提出质疑 | 明确 question/user_claim/system_hypothesis；校验用户断言原文及消息来源，相关单元和真实记录保留 |
| 记忆只复述旧缺口，没推进研究 | 用户指出“记住”不等于好用 | 接入公告/PDF补查、保存已解决和未决问题、恢复证据定位；有真实续接实例，仍有补查失败 |
| 停用记忆后仍可能自动写入 | 对照交接 M09 要求审查 | 读取和提交阶段同时受策略/版本约束；停用、删除及迟到写回机制有回归 |
| 扶摇默认参数冲突 | 实际返回 code=1004，limit 与 start/end 冲突 | 使用单一最近 N 期模式，再严格筛选用户要求期间；缺期不自动换期 |
| 模型提取扩写单位、年度列或用错口径 | 原文引文、勾稽及最终核验拒绝 | 收紧提取合同，预算内一次格式恢复；没有降低标准强行发布，失败仍记录 |
| DeepSeek 请求 400 与格式差异 | 实际连接失败及模型 ID/基址检查 | 使用当前验证配置和 JSON Object 适配；兼容请求结构与服务端 Schema 分开校验 |
| Render 构建找不到 vite | 首次部署日志 `vite: not found` | 生产构建显式安装开发依赖，CI 与 Render 后续部署成功 |
| MCP 工具发现网络失败 | 公网真实任务失败 Trace | 握手/发现增加一次有限重试、底层错误码脱敏记录；新增 5 项测试，重新部署后真实任务完成 |

## 四、验证时保留的边界

- 合成故障、构造关注、真实模型调用、真实数据与用户效果分别标注。
- 本机成功、接口握手、构建通过和最终核验通过，均不代替端到端任务完成或长期用户价值。
- 失败未通过修改记录、重复抽样筛选或放宽引用要求改成成功。
- 当前公开仓库排除了凭证、个人研究状态和原始调用日志；按源码版本与测试汇总定位证据。
- 对“越用越好”的承诺仍需连续使用观察；现阶段证明的是部分机制及有限任务能运行。
