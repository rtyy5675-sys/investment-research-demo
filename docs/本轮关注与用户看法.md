## 本轮取舍

保留现有浅色 Agent 对话页，调整信息层次：一条可修改的关注、两三项分析、一个主要未决条件与当前可执行动作。历史轮次、其他条件和原始资料按需展开。没有新增角色架构；用户可以在主 Bot 完成核心任务。

本次设计取值：视觉变化 3/10、动效 1/10、信息密度 5/10。动效沿用原输入区反馈，新增操作不使用等待动画作装饰。品牌、地址和 Bot 导航保留。

## 实现合同

### 本轮关注

`task.focus` 保存文字、`source: ai/user`、版本和范围。AI 提炼的问题理解显示“问题理解·可修改”；只有用户明确修改的文字才显示“由你明确”。

`POST /api/tasks/:id/focus` 使用 `expectedRevision`、`expectedFocusVersion` 和 `operationId`。它启动新的分析版本并取消旧请求，锁定已确认的公司和报告期，优先复用同范围证据。明确换公司或期间时引导使用“修改研究问题”，不偷偷替换范围。目前需先取得一次完整的 MCP 分析；运行中的关注修改需等待当前操作或使用原有修改问题入口。

### AI 分析

每项分析保存待检验 `claim`、解释 `answer`、证据 ID，以及相对该主张的 `supports / contradicts / insufficient`。这些关系是 AI 分析，不是用户立场，也不是独立金融专家已审查的事实标签。

结果保存自己的关注与范围快照。模型规划、核验与解读使用同轮关注；用户看法不作为研究指令注入模型。发布仍受任务版本、同公司期间、引用白名单约束。可执行补查的工具 ID 必须来自本轮剩余目录，点击后服务器锁定该工具与原范围；已足够回答时允许结束。

### 用户看法

`task.userView` 独立保存 `version`、`draft` 与追加的 `confirmations`。`POST /view` 不调用研究模型，不启动新的研究版本，不自动创建观点。

首版直接保存用户原话，没有自动整理立场。用户先保存草稿，阅读后再确认。确认记录包含原话、确认文本、对应分析与关注版本、范围和时间。新分析、失败或换范围均不更新旧确认；界面提示它仍对应原版本。修改看法需要再次保存和确认，旧确认保留。

接口用版本比较和操作幂等防止静默覆盖或重复确认。分析已经更新时，旧稿不能直接确认为新版观点；需要复核后重新保存。前端用 `stateVersion` 拒收迟到的同轮旧状态，记录写入冲突时同步最新状态并保留正在编辑的文本。服务按 ID 共享首次加载，避免冷启动并发读取产生不同任务对象。

`POST /finish` 只记录本轮研究结束，不生成、确认或更新用户看法。允许未记录看法就结束。

## 真实发现与修复

1. 轮询时关注区出现重复节点。原因是关注组件与用户记录组件使用相同 React key；已分开 key，并在真实轮询后检查只各有一个节点。
2. 首版证据标签评价对象不清。一组态度重放里，同一“不足以判断销量”曾分别标为 supported 与 limited。现改为显式 claim，并让标签只评价证据与 claim 的关系；原失败与后续对照均保留。
3. 空补查问题原可通过校验，现拒绝空问题或理由，并约束实际补查工具。
4. 首次加载会话的并发读取原可能形成两个任务对象，现按 ID 共享加载 Promise。
5. 已确认一条历史回答的差额错误：“928.26至969.90亿元，增加41.16亿元”。按展示值应为41.64亿元。历史页面显示明确更正提示，原运行文件不改；用户原话从不自动更正。新回答可使用程序从原始字段计算的差额与正基期同比，发布前也检查这一类明确的“起额→止额→变化额”表达。

金额检查只覆盖识别到的亿元起止额表达；它不覆盖所有句式、比率、因果或来源真伪。不能因此宣称数值可靠性已全面解决。原始字段和原始错误记录继续可查。
