# 效果评测、上下文与用户观察

更新：2026-10-15。本文件给出可复用判据和本地评测工具；不是已完成用户研究或金融正确率报告。

## 当前提供的能力

- `evaluation/cases.json`：8 个案例，分别覆盖经营理解、引用语义、期间变更、证据更新、部分工具失败、停止/预算、上下文与观点归属、保存失败。每题规定必须回答、禁止推断、补查与结束条件、异常行为及用户观察问题。
- `scripts/evaluate-research.mjs`：读取已有本地任务 JSON；不访问模型、MCP 或网络。检查结果结构、引用 ID、范围标识和动作字段；金融语义、异常实测、用户理解默认 `pending`。
- `evaluation/manual-review.example.json`：人工记录格式。表述结论需要指出对应最终句子及来源字段/原文；不能只写“看起来正确”。
- `lib/research-context.mjs`：按字符预算选择任务原话与工作快照。它是确定性任务台账，不是模型对用户立场的理解。

## 本地执行

```sh
node scripts/evaluate-research.mjs \
  --task artifacts/tasks/<task-id>.json \
  --case business-understanding \
  --output artifacts/evaluation-<task-id>.json
```

可选追加 `--review /绝对路径/manual-review.json`。`caseId` 必须与案例一致。退出码：`0` 表示结构项通过；`1` 表示至少一个结构项失败；`2` 表示输入/使用方式错误。`0` **不表示任务已完成、金融正确或用户已理解**。脚本不会自动选取“适合任务”的案例，审查者需先确认输入与所选案例匹配。

输出中先看 `automatedStructure`，再逐项填写 `financialSemantics`、`exceptionBehavior`、`userUnderstanding`。每项的 `index` 与输出一致，人工项必须填写 `pass/fail` 及非空 `evidence`。没有填到的项保留 `pending`；任一项失败使该节失败。人工结果要求具名标识 `reviewer` 和 `reviewedAt`，它只是审查记录，脚本不能验证审查者身份或证据真实性。

用户理解项必须有 `observationType: observed_user_session`、`sessionId` 和去标识的 `participantId` 才会被计入。内部桌面评审使用 `desk_review`，不能冒充真实用户观察；仅人工自称观察也不等同于已由系统独立验证。

## 怎样判“答到了”

每题都要先写出一份依据原始材料的人工答案要点：本轮可知的事实、不能推出的结论、最关键缺口以及能接受的下一步。不能只检查“没犯错”。即使每句话都安全，未解释本来可以回答的重要事实，仍判未完成。

核心主张通过需同时满足：数值和期间与原始来源一致；引用确实支持该句；解释与事实分开；解释没有越过现有证据；关键缺口与当前问题相关。引用表格存在、模型使用了 `insufficient`、工具成功，都不能单独使语义项通过。历史错误记录应原样保留，并记录修正后的对应结果。

一条链路通过至少要求：原始问题 → 有出处的事实 → 局部判断 → 一次关键补查或清楚的可终止边界 → 更新后判断。补查不可得可以诚实局部回答，但不能说完整用户任务已解决。失败/停止/预算/保存等案例需真实操作或受控故障，不能从代码存在推定运行通过。

## 数据边界

本案例目录不内置真实公司的财务数值或投资结论。研究任务可用真实 MCP 返回或公司原始披露；审查记录保存公司、期间、来源/抓取时间、字段与单位，说明供应商可能重述、不是历史时点快照等限制。结构测试中的“示例公司/数值”只能作为合成测试夹具，不得冒充真实金融事实或真实用户需求记录。

如果复用已有任务，记录模型/Prompt 版本和任务版本；旧的固定快照不能自动证明当前模型链路表现。自动检查引用支持标识仅做枚举检查，不判断支持方向是否正确，不计算金融正确率，不独立判别因果、估值或长期风险。

## 同资料、同工具的有限对照

选择一条目标用户真实发生过的问题，记录他原来怎么做及卡住位置。当前产品与“有相同工具的单助手”使用同一问题、同一公司期间、同样原始资料和工具权限；记录模型版本、调用/时间预算以及实际用量，不让一方额外取证后把优势归因于角色划分。

同一个人做两种方式可能产生学习效应。小样本时至少交替先后顺序或使用两个难度相近的问题，并诚实记录材料差异。比较是否回答了必要事实、是否发现关键缺口、下一步是否可执行、错误推断及耗时。不以角色数量、调用成功、报告长度、主观“看起来专业”作为成功指标。

3–5 位观察可用于发现具体误解和交互障碍，不是统计可靠性证明。24 小时内可先做一条完整观察与一条有限对照；若没有实际参与者，用户理解保持待验证。

## 用户观察记录模板

| 字段 | 填写内容 |
| --- | --- |
| sessionId / participantId / 日期 | 去标识记录；不填姓名、资产或账号 |
| 问题来源 | 用户最近真实发生的任务；非候选人编造的问题 |
| 原有做法 | 用了哪些工具、卡在哪里、是否解决；如无记录写未知 |
| 本轮任务与资料 | taskId、revision、公司、期间、来源、Prompt/模型版本 |
| 对照顺序与预算 | 先后方式、工具权限、资料和实际调用/耗时 |
| 读前理解 | 用户原话，不能替他纠正后再记录 |
| 理解问题一 | “现在最能确认哪一件事？”用户原话与判定依据 |
| 理解问题二 | “哪件事仍不能下结论，为什么？”用户原话与判定依据 |
| 理解问题三 | “什么新证据会改变你的理解？”用户原话与判定依据 |
| 下一步 | 用户实际选择了什么；只口头说会做时注明未实际执行 |
| 误解或失败 | 对应页面/回答句子、是否自行发现、是否需要提示 |
| 判定与取舍 | 必要事实完成/缺失、严重误读、有帮助的步骤、下一项改动 |

观察问题用于研究验收，不应强行放进产品，让每位用户答完测验才能继续。允许用户不保存立场，不把投资意愿或是否赞同 AI 当成理解程度。

## 有界上下文接口

```js
import { buildResearchContext } from './lib/research-context.mjs';
const taskContext = buildResearchContext(task, { maxChars: 18000, maxRecentMessages: 8 });
// 旧接口如需要字符串数组：
const questionHistory = taskContext.recentQuestions.map(item => item.text);
```

返回 `summary`、带定位的 `recentQuestions`、`truncation` 与 `estimatedInputTokens`。摘要保留本次原始任务目标、用户明确修改的关注、范围与已有分析版本、用户原话选择、关键未决条件、证据 ID、失败/恢复信息。`userView` 不进入摘要。新 `revise` 是原话选择的边界；旧分析/证据在新取证前仍可能留在任务对象上，因此快照标明其分析版本，调用方以本轮独立传入的 `scope/evidence` 为准，不把旧快照当新事实。

前两条原话与近期消息并存；还支持 `task.contextPinnedMessageIds` 明确固定原文。没有做语义模型分类，不能宣称“已理解并保留全部约束”。省略时有数量、原消息索引、ID/版本及截断原文区间；需要时回到 `task.messages` 原文复核。近期问题是带 ID/版本的对象，不要把它误当字符串。

字符预算约束完整返回值的 JSON UTF-16 长度，最低 `3000`；默认 `18000`。它不限制模型输入中另外提供的系统规则和真实证据，调用方还须控制整段输入预算。`estimatedInputTokens = ceil(JSON字符数 / 2)` 仅用于粗略观察；没有使用模型 tokenizer，不能保证模型上下文窗口或成本。异常大的结构元数据可能导致明确拒绝，应增加预算或缩小结构，而非静默丢失关键字段。

`task.contextSummary` 建议存完整返回对象，避免丢失裁剪标记。失败事件保留 callId/revision/attempt/category 等；重试检查点由执行层保存，这个模块只读取并提供定位，不执行恢复。

## 本轮验证边界

`node --test tests/research-context.test.mjs` 已通过 7 项：早期原话保留、revise 边界、有界裁剪定位、失败与关注归属、固定原话与非法预算、结构与语义区分、桌面评审不能冒充用户理解。

这些是确定性模块测试。本模块不调用模型/MCP，本轮没有因此新增真实用户理解结论；8 个案例定义完成不等于8个案例已运行通过。
